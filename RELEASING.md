# Releasing Lurk

## Cutting a release

Everything is driven by a tag. From a clean `main`:

```bash
git switch main && git pull

npm run release -- minor --dry-run   # check what it will do
npm run release -- minor             # bump, roll the CHANGELOG, commit, tag

git push origin main --follow-tags   # this is what starts the build
```

`npm run release` accepts `patch`, `minor`, `major`, or an explicit version
(`0.3.0-rc.1`). It refuses to run on a dirty tree, off `main`, on a tag that
already exists, or when the `[Unreleased]` CHANGELOG section is empty — the
release notes come from that section, so an empty one means a release nobody
can read.

Which of patch/minor/major to use: [docs/VERSIONING.md](docs/VERSIONING.md).

## What the tag triggers

`.github/workflows/release.yml`, in three stages:

1. **Verify** — tag matches `package.json`, CHANGELOG has a section for the
   version, then lint + unit + smoke tests. Nothing is built until this passes.
2. **Build** — Windows, macOS and Linux runners each build their installers and
   upload them into the *same draft* GitHub release.
3. **Publish** — generates the release notes and flips the draft to published.

The draft-until-complete order is deliberate. electron-builder writes the
`latest*.yml` manifests that the auto-updater reads, and a release published
before every platform has uploaded would advertise an update whose file does
not exist yet. Publishing last means installed copies never see a partial
release.

> The `v0.1.0` release sat as an unpublished draft for exactly this reason —
> the old workflow had no publish step, so nothing ever went live and no
> installed copy could have found an update.

## Release notes

Generated by `scripts/release-notes.mjs`:

- the `CHANGELOG.md` section for the version — the human-written part
- a collapsed list of commits since the previous tag, as a backstop
- an install table saying which file to download per platform
- a compare link to the previous tag

To preview before tagging:

```bash
node scripts/release-notes.mjs 0.2.0
```

## Auto-update, per platform

| Platform | Package | Behaviour |
| --- | --- | --- |
| Windows | NSIS `.exe` | Downloads in the background, offers **Restart**. |
| Linux | `.AppImage` | Downloads in the background, offers **Restart**. |
| Linux | `.deb`, `.pacman` | Detects the new version, shows a banner and a desktop notification, links to the download. |
| macOS | `.dmg` | Same as above — notify only. |

The split is in `lib/update-mode.js`. AppImage is the only Linux format
electron-updater can rewrite in place; `.deb` and `.pacman` are owned by the
system package manager, and it would be wrong for the app to fight it. macOS
becomes automatic once the app is signed with a Developer ID — Squirrel.Mac
refuses to apply an update to an unsigned bundle.

**On Arch/Omarchy, install the AppImage** if you want updates to arrive by
themselves.

### What the user sees

The app checks 8 seconds after launch and every 6 hours after that. When
something is found:

- a desktop notification (mako/dunst under Hyprland, and the native centre
  elsewhere), and
- a banner in the bottom-right of the window, with **Restart** or **Download**.

Dismissing the banner is remembered per version, so a background re-check does
not re-nag about a release already waved off. There is also a manual
**Check for updates** button in the sidebar footer, next to the running version.

Updates are off entirely in an unpackaged dev run (`npm start`).

## Testing an update end to end

Auto-update cannot be exercised from source — it needs two real packaged builds.

1. Release the current version, e.g. `0.2.0`.
2. Install it properly (AppImage on Linux, the NSIS installer on Windows).
3. Release `0.2.1`.
4. Launch the `0.2.0` install and wait ~8 seconds.

Expect a notification, then a banner offering **Restart**. If nothing appears,
check in this order:

- Is the GitHub release **published**, not a draft? Drafts are invisible to the
  updater.
- Does the release have `latest.yml` (Windows) or `latest-linux.yml` (Linux)?
  The publish job warns when one is missing.
- On Linux, is the app running from an AppImage? `echo $APPIMAGE` must be set;
  otherwise it is correctly in notify-only mode.
- Is the installed version actually lower than the release?

## Signing

Builds are currently unsigned. This means Windows shows a SmartScreen warning
on first install, and macOS cannot auto-update at all. The release workflow
already reads `CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`,
`APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` from repository secrets and
signs when they are present — adding the certificates is the only step left.
Tracked in #23.

## If a release goes wrong

The tag is the only thing that matters, and nothing is visible to users until
the publish step runs.

```bash
# before it is published — delete the draft and the tag, fix, re-cut
gh release delete v0.2.0 --yes
git push --delete origin v0.2.0
git tag -d v0.2.0
```

If it is already published and broken, do not delete it — installed copies may
already have downloaded it. Cut a `0.2.1` with the fix instead, and mark the bad
release as a prerelease so it stops being offered:

```bash
gh release edit v0.2.0 --prerelease --latest=false
```
